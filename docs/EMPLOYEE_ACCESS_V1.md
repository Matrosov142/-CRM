# Управление доступом сотрудников — v1.0

## Реализовано
- Директор может создать приглашение сотруднику.
- Разрешённые роли: специалист по тендерам, менеджер по закупкам, склад, логистика, бухгалтерия.
- Генерируется криптографически случайный токен; в БД сохраняется только SHA-256 хеш.
- Приглашение действует 72 часа; повторное приглашение отзывает предыдущее непринятое приглашение для того же адреса.
- Принятие приглашения создаёт пользователя (если его ещё нет) и активное членство компании.
- Повторное использование, истёкший или отозванный токен отклоняется.
- Создание и принятие приглашения записываются в журнал аудита.
- Отправка по email не реализована: API возвращает токен один раз для ручной передачи.

## API
- `POST /api/v1/employees/invitations` — создать приглашение (только директор).
- `POST /api/v1/employees/invitations/accept` — принять приглашение и задать пароль.

## Ограничения
- Список сотрудников и отзыв существующего членства не включены: действующая RLS-политика `memberships` разрешает пользователю видеть только собственные членства. Обходить её из API нельзя.
- Для безопасного управления чужими членствами нужна отдельная проверенная директорская RLS-политика.
- Изменение роли после принятия, MFA, подтверждение email, почтовая доставка и защита от конкурентного принятия требуют следующих этапов.
- Нужны PostgreSQL integration tests на отдельной disposable БД для проверки RLS и одновременного принятия токена.
- После принятия приглашения пользователь входит через `/api/v1/auth/login`.


## Управление активными сотрудниками (v1.1)
- `GET /api/v1/employees` — список сотрудников компании (только директор).
- `PATCH /api/v1/employees/{membership_id}/role` — смена роли (только директор).
- `POST /api/v1/employees/{membership_id}/revoke` — отзыв доступа (только директор).
- Нельзя менять или отзывать собственную роль/доступ через эти операции.
- Нельзя понизить роль другого директора через смену роли.
- Нельзя отозвать доступ последнего активного директора.
- Все изменения записываются в журнал аудита.

### RLS для управления членствами
Миграция `0006_director_membership_management` добавляет директорскую политику.
Функция `app_is_company_director()` выполняется с правами владельца таблицы, чтобы проверить
директорское членство без рекурсивного срабатывания RLS. Поэтому обязательны условия:
1. Runtime-пользователь БД не владеет таблицами и не имеет `BYPASSRLS`/`SUPERUSER`.
2. Владельцем таблиц и функции остаётся отдельная миграционная роль, не используемая приложением.
3. Перед production обязательны PostgreSQL-тесты с runtime-ролью и отдельной disposable БД.
