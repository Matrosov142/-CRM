## Назначение

Эта сборка предназначена для закрытого технического пилота с вымышленными данными. Она НЕ допущена к обработке реальных персональных, договорных, финансовых или коммерческих данных.

## Состав

- PostgreSQL 16 с постоянным Docker volume.
- FastAPI API.
- React/Vite frontend, собранный в nginx.
- `potok_admin` — административная роль PostgreSQL, доступна только одноразовому `db-bootstrap`.
- `potok_owner` — отдельный non-superuser владелец схемы для Alembic.
- `potok_runtime` — отдельная роль API: не владелец таблиц, без SUPERUSER/BYPASSRLS.
- Хранилище файлов в отдельном volume.
- API и PostgreSQL не опубликованы на хостовые порты.
- Веб-интерфейс доступен только на `127.0.0.1:18080`.

## Требования

- Linux x86_64.
- Docker Engine и Docker Compose plugin v2.
- 2 vCPU / 4 ГБ RAM минимум для закрытого пилота; 4 vCPU / 8 ГБ RAM предпочтительнее.
- 10 ГБ свободного диска минимум.
- HTTPS reverse proxy или доступ только через VPN. Не публиковать порт 18080 напрямую в интернет.

## Установка

Распакуйте архив в отдельный каталог, затем:

```bash
bash ops/pilot-up.sh
```

Скрипт:
1. Создаёт `.env.pilot` с четырьмя случайными секретами (DB admin, schema owner, runtime, JWT), права файла 600.
2. Собирает API и frontend контейнеры.
3. Запускает PostgreSQL.
4. Создаёт `potok_owner` и `potok_runtime` через `potok_admin`.
5. Применяет миграции от имени non-superuser `potok_owner`.
6. Выдаёт `potok_runtime` ограниченные права и запускает API и web.

`db-migrate` кратковременно получает `DB_OWNER_PASSWORD`, owner `DATABASE_URL` и `JWT_SECRET`, поскольку Alembic импортирует приложение и его настройки. Это отдельный одноразовый контейнер; постоянно работающий `api` получает только runtime `DATABASE_URL` и `JWT_SECRET`. Штатный `ops/pilot-up.sh` удаляет завершившиеся bootstrap/migration containers после успешного запуска.

Проверка готовности:

```bash
curl -fsS http://127.0.0.1:18080/api/v1/health/ready
```

Ожидается JSON со статусом `ready`.

## Создание первого директора

Открытая регистрация отключена. Первый директор создаётся одноразовым контейнером, которому пароль администратора БД передаётся только на время команды; постоянно работающий API этот секрет не получает. После запуска выполните отдельную одноразовую команду через bootstrap-контейнер:

```bash
docker compose --env-file .env.pilot -f compose.pilot.yml run --rm --no-deps \\
  --entrypoint python db-bootstrap -m ops.create_first_admin
```

Введите email, название компании и пароль не короче 14 символов. Команда разрешает создание только если таблица пользователей пуста. Пароль вводится интерактивно и не отображается.

Затем откройте интерфейс через локальный reverse proxy и войдите.

## HTTPS через Caddy

Сначала настройте DNS принадлежащего вам домена на IP сервера. Не используйте домен-пример ниже буквально.

Готовый пример находится в `ops/Caddyfile.pilot.example`. Пример отдельного блока Caddy:

```caddy
crm.ВАШ-ДОМЕН {
    encode zstd gzip
    reverse_proxy 127.0.0.1:18080
}
```

Добавляйте блок только после резервной копии текущего Caddyfile и проверки конфигурации. Не заменяйте существующие сайты/сервисы. После изменения проверьте `caddy validate` и только затем делайте reload.

```bash

```

Контейнеры останавливаются, именованные тома сохраняются. Не добавляйте `-v`, если не хотите удалить постоянные данные.

## Складской API: резервы и частичная отгрузка

После создания резерва клиент получает его идентификатор. Чтобы показать состав резерва и сформировать частичную отгрузку, используйте:

```http
GET /api/v1/warehouse/reservations?status=active
```

Ответ содержит `lines[].id` — это `reservation_line_id`, обязательный для `POST /api/v1/warehouse/shipments`. Также возвращаются `quantity`, `quantity_shipped` и `quantity_remaining`. Доступ к резервам ограничен текущей компанией и проверяется серверной ролью. Физический остаток уменьшается только при подтверждении отгрузки.

## Ограничения пилота

- Авторизация использует bearer JWT в `localStorage`. Не использовать реальные данные до перехода на HttpOnly cookie/session, CSRF-защиты и проверки XSS.
- Панель директора содержит демонстрационные KPI.
- Не все бизнес-модули имеют полноценные рабочие экраны. API отдельных модулей требует приёмочных сценариев.
- Нет завершённого OCR сканов, антивирусного сканирования файлов, MFA и восстановления доступа.
- Нет проверенной интеграции с 1С, ЭДО, банками и тендерными площадками.
- RLS и миграции должны пройти полный тест на целевой PostgreSQL перед пилотом.
- Доступ к приложению должен быть ограничен VPN/IP allowlist, пока не завершён security review.
- Не загружайте персональные данные граждан РФ, пока не проверены локализация, поручение обработки, договоры, модель оператора и меры защиты по 152-ФЗ.

## Критерии приёмки пилота

1. Все миграции успешно применяются на чистой PostgreSQL 16.
2. API работает от `potok_runtime`, не от владельца БД.
3. Компания A не может читать/изменять записи компании B.
4. Все роли проверены на серверной стороне.
5. Создание, приёмка, резерв и отгрузка не создают отрицательных остатков при конкурентных запросах.
6. Платежи и распределения не закрывают обязательства сверх подтверждённых сумм.
7. Документы скачиваются только в пределах компании и после проверки прав.
8. Backup успешно восстановлен в отдельной среде.
9. HTTPS, ограничение сетевого доступа и мониторинг проверены.
10. Пользовательские сценарии пройдены на вымышленных данных.


## Расчёт доставки (Pilot 0.4)

API `POST /api/v1/transport/estimate` сравнивает введённые тарифы транспортных компаний с расчётом собственного транспорта. Требуются адреса отправления/назначения, вручную подтверждённое расстояние в одну сторону, описание груза и хотя бы один вариант доставки. Для перевозчика можно передать фактическое коммерческое предложение (`quoted_total`) либо тариф: подача + ставка за км + погрузка + разгрузка + платные дороги + страхование + дополнительные расходы. Для собственного транспорта учитываются расход топлива, цена топлива, водитель, амортизация, обслуживание, платные дороги и погрузочно-разгрузочные расходы; по умолчанию учитывается обратный путь.

Доступ: директор, логист, менеджер закупок. Все суммы в RUB. Результат — оценка для сравнения, не заказ перевозки. Геомаршрут, пробки, тарифы перевозчиков, ограничения по габаритам/весу и доступность машин автоматически пока не запрашиваются. Перед выбором подтвердить коммерческое предложение и сроки у перевозчика. Автоматического бронирования/диспетчеризации нет.


## Интерфейс расчёта доставки — Pilot 0.5

В русскоязычном интерфейсе после входа доступен раздел «Расчёт доставки». Форма отправляет данные в `POST /api/v1/transport/estimate` и отображает сравнение тарифа перевозчика с собственным транспортом. Для перевозчика можно внести цену из коммерческого предложения. Параметры собственного транспорта включают топливо, водителя, амортизацию и обслуживание. Раздел доступен пользователю с ролью директора, логиста или менеджера закупок. Показатели главной панели по-прежнему демонстрационные.


## Сохранение расчётов — Pilot 0.6

Расчёт доставки сохраняется в PostgreSQL в таблице `delivery_estimates`, с tenant RLS, составом вариантов, автором и временем. `GET /api/v1/transport/estimates` возвращает историю компании. `POST /api/v1/transport/estimates/{id}/select?option_index=N` сохраняет ручной выбор логиста/директора и пишет событие в аудит. В интерфейсе доступны просмотр истории и выбор варианта. Выбор не является заказом перевозки.

## Допуск к предпилоту — 2026-11-10

До подключения пилотных клиентских данных пройдите пункты [контрольного листа допуска](RC1_PRE_PILOT_ACCEPTANCE_RU.md): независимая security оценка; тестирование целевого TLS/reverse proxy/мониторинга/секретов в staging; backup encryption, retention и restore с замером RPO/RTO; формальная бизнес-приёмка синтетических сценариев; юридическая и hosting-проверка.
