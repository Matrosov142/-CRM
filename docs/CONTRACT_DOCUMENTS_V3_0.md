# Документы договоров v3.0

## Возможности
- Карточка документа с привязкой к договору и видом документа.
- Загрузка исходного файла потоково, без сохранения в публичный каталог.
- Неизменяемые версии: номер, исходное имя, MIME-тип, размер, SHA-256, автор и дата.
- Новая версия создаётся отдельной записью; предыдущая не перезаписывается.
- Виды: договор, дополнительное соглашение, счёт, накладная, УПД, акт, спецификация, прочее.
- Лимит файла 25 MiB; разрешены PDF, JPEG, PNG, TIFF, DOC/DOCX, XLS/XLSX.
- Файлы хранятся вне web-root по `DOCUMENT_STORAGE_PATH`; каталог и файлы создаются с ограниченными правами.
- RLS и составные внешние ключи ограничивают принадлежность компании.

## API
`POST /api/v1/documents?title=...&document_kind=contract&contract_id=<uuid>` — тело запроса содержит байты файла, `X-File-Name` содержит исходное имя, `Content-Type` — MIME-тип.
`GET /api/v1/documents?contract_id=<uuid>&document_kind=addendum` — список метаданных и версий.
`POST /api/v1/documents/{id}/versions?note=...` — новая версия, тело — байты файла.
`GET /api/v1/contracts/{id}/documents` — документы договора.

## Важные ограничения
- API выдаёт метаданные, но не отдаёт файл на скачивание; безопасный endpoint скачивания и проверка антивирусом должны быть следующим этапом.
- SHA-256 подтверждает целостность файла, но не подлинность подписи. Электронная подпись и ЭДО не реализованы.
- OCR, автоматическое извлечение реквизитов и сверка с заказом не реализованы.
- Для production нужно настроить резервное копирование каталога документов, мониторинг свободного места, антивирусную проверку, TLS и отдельные права runtime-пользователя.
- Файловое хранилище должно находиться в РФ при обработке персональных данных граждан РФ; регион и договорные условия инфраструктуры проверяются отдельно.
- PostgreSQL миграция и RLS требуют интеграционной проверки на реальной БД под runtime-ролью без BYPASSRLS.
