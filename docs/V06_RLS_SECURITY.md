# v0.6 — PostgreSQL RLS для ядра

## Защита
- `memberships`: запросы и изменения видят только членства текущего пользователя (`app.user_id`).
- `companies`: доступ только к компаниям, где текущий пользователь имеет активное членство.
- `FORCE ROW LEVEL SECURITY` включён для обеих таблиц.
- Контекст задаётся через `set_config(..., true)` и действует только в пределах транзакции.
- Вход сначала проверяет пользователя, затем устанавливает `app.user_id` для безопасного поиска только его членств; после выбора компании устанавливает контекст компании.

## Обязательная эксплуатационная настройка
Миграции выполняются отдельной ролью-владельцем. Приложение должно подключаться отдельной runtime-ролью, которая:
- не является владельцем таблиц;
- не имеет `SUPERUSER` и `BYPASSRLS`;
- имеет только необходимые `SELECT/INSERT/UPDATE/DELETE` права;
- не имеет права менять схему или создавать роли.

RLS не защищает от суперпользователя/роли с `BYPASSRLS`. Не запускайте приложение под владельцем миграций.

## Важные ограничения
- Таблица `users` остаётся глобальным каталогом учётных записей для входа; она не содержит tenant-owned бизнес-данные. В API нельзя добавлять endpoint общего списка пользователей.
- Регистрация компании отключена по умолчанию. Bootstrap с включённым флагом пока несовместим с RLS без отдельной безопасной процедуры администрирования; не включать флаг в интернет-доступной среде.
- Бизнес-таблицы ещё не добавлены в миграции v0.6, поэтому политика RLS пока применена только к `companies` и `memberships`.
- Реальные PostgreSQL integration tests ещё должны быть выполнены в изолированной тестовой БД с runtime-ролью.
